# V1.3-B — Authentication & Security Audit

## Scope

This phase hardens the access model without changing the existing QR upload UI or the public PDF upload flow.

## 1. Authentication / application access

The QR upload page remains public by design: a customer scans the QR code and uploads a PDF without entering credentials.

The internal Quick Print queue is not public. Queue operations require `JOB_API_KEY` through the `X-API-Key` header.

Protected endpoints:

- `GET /api/jobs`
- `GET /api/jobs/:jobId`
- `GET /api/jobs/:jobId/file`
- `DELETE /api/jobs/:jobId`
- `POST /api/jobs/:jobId/claim`
- `POST /api/jobs/:jobId/status`

This separation is intentional: public upload, private queue control.

## 2. API key protection

`JOB_API_KEY` is read only from the server environment. It is not embedded in the HTML or browser JavaScript.

Production rules:

1. Set a long random secret in the NAS container environment.
2. Do not put the real key in Git, QR URLs, browser code, screenshots, or logs.
3. Do not expose queue endpoints directly to the Internet.
4. Keep the key available only to the Quick Print client/server that needs queue access.
5. Rotate the key if it is ever exposed.

The public `POST /api/upload` endpoint intentionally does not require this key because it is the customer-facing QR operation.

## 3. Existing upload protections audited

- Maximum upload size: `MAX_FILE_MB`.
- Streaming upload instead of buffering the entire PDF in memory.
- Basic PDF signature validation using `%PDF-`.
- Filename is reduced to a basename and unsafe filename characters are sanitized.
- Job IDs use random bytes and a restricted format.
- Storage is outside the public HTML path.
- Queue endpoints reject missing/incorrect API keys.
- `Cache-Control: no-store` is used on responses.

## 4. Internet exposure rule

Do not publish the Node.js port directly to the Internet.

Target deployment path:

`Internet -> HTTPS/Cloudflare -> reverse proxy/tunnel -> QR Upload container`

Cloudflare and reverse-proxy configuration are separate V1.3 phases so that authentication is validated before Internet exposure.

## 5. Not yet included in V1.3-B

These are deliberately deferred to later phases:

- persistent audit logging
- automated cleanup/retention
- backup jobs
- distributed rate limiting/concurrency controls
- final stress/security test
